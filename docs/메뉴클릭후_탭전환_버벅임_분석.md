# 메뉴 클릭 후 탭 전환 버벅임 — 원인 분석 및 수정 기록

- 날짜: 2026-07-14
- 증상: 앱 실행 직후에는 탭(wooko ↔ Downloads) 전환이 부드럽지만, **상단 메뉴(파일, 선택 등)를 한 번이라도 클릭한 뒤부터** 탭 전환이 버벅이기 시작하고, 앱을 재시작하기 전까지 돌아오지 않음.

## 결론 (원인)

**메뉴 팝업이 처음 열리는 순간, Windows에 상주하는 UI 자동화(UIA) 클라이언트(한글 IME `ctfmon`, `TextInputHost` 등)가 이 프로세스에 접근성 이벤트 리스너를 등록한다.** 그때부터 WPF는 `AutomationPeer.ListenerExists() == true` 상태가 되어 창 전체에 접근성 이벤트를 발행하기 시작하며, 이 등록은 **프로세스가 끝날 때까지 해제되지 않는다.**

이 앱은 탭 전환 시 `SelectedLeftTab`/`SelectedRightTab` setter가 `LeftPanel`/`RightPanel` 변경을 통지해 **DataGrid 전체가 다시 바인딩**되는 구조라, 리스너가 켜진 뒤에는 전환할 때마다:

1. 모든 행/셀의 AutomationPeer(접근성 트리)를 다시 생성하고
2. structure-changed 등 UIA 이벤트를 대량 발행

하는 비용이 렌더 패스에 얹혀 UI 스레드를 600ms~1.3초씩 점유 → 체감 버벅임.

즉 메뉴 자체가 느린 게 아니라, **메뉴가 "접근성 이벤트 모드"를 켜는 방아쇠**였다.

## 진단 근거

### 계측 방법

- `Helpers/LiveTrace.cs`의 `WriteProcessSnapshot()`에 UIA 리스너 상태(`uia[struct,prop,focus,selAdd]`) 로깅 추가
- `Helpers/DispatcherDiag.cs` 신설: 30ms 이상 걸린 디스패처 작업을 우선순위·메서드명과 함께 `live_trace.log`에 기록 (Debug 빌드 전용, `App.OnStartup`에서 `DispatcherDiag.Init(Dispatcher)`로 활성화)
- UIA 자동화 스크립트로 재현: 탭 전환 12회 → `파일(F)` 메뉴 열고 닫기 → 탭 전환 12회

### 수정 전 측정 결과

| 구간 | UIA 리스너 | 렌더 패스 1회 (`MediaContext.RenderMessageHandler`) | 디스패처 유휴 도달 (`render-complete`) |
|---|---|---|---|
| 메뉴 열기 전 | 전부 `False` | 73–194ms | 135–349ms |
| 메뉴 1회 개폐 후 | 전부 `True` | **613–1351ms** | **최대 11,860ms 지연 (누적 적체)** |

- 메뉴가 열리는 정확히 그 시점에 `uia[...]` 플래그가 `False → True`로 전환됨 (GDI/USER 핸들 증가와 동시)
- 사용자 수동 재현 로그에서도 동일 패턴 확인 (메뉴 클릭 후 `render-complete` 2,712ms까지 적체)
- 당시 시스템에 상주 중인 UIA 클라이언트: `ctfmon`(한글 IME/TSF), `TextInputHost`

## 적용한 수정

`Controls/AutomationQuietDataGrid.cs` 신설 — `OnCreateAutomationPeer()`를 오버라이드해 **행/셀 자식 피어를 노출하지 않는**(GetChildrenCore가 빈 목록 반환) 단일 피어를 반환하는 DataGrid 서브클래스.

`MainWindow.xaml`에서 파일 목록 DataGrid 3곳을 교체:

| 위치 | 변경 |
|---|---|
| 좌측 패널 `LeftPanelGrid` | `<DataGrid>` → `<controls:AutomationQuietDataGrid>` |
| 우측 패널 `RightPanelGrid` | `<DataGrid>` → `<controls:AutomationQuietDataGrid>` |
| 4패널 그리드 (`Tag="{Binding}"`인 그리드) | `<DataGrid>` → `<controls:AutomationQuietDataGrid>` |

내부의 `<DataGrid.Columns>`, `<DataGrid.Style>` 등 프로퍼티 요소와 암시적 DataGrid 스타일(`BasedOn` 경유)은 그대로 유효.

### 수정 후 측정 결과 (동일 시나리오)

| 구간 | 렌더 패스 1회 | 디스패처 유휴 도달 |
|---|---|---|
| 메뉴 개폐 후 (UIA 리스너 `True`) | 32–239ms | 124–376ms, 적체 없음 |

→ 메뉴를 연 뒤에도 열기 전과 동일한 성능. 수정 목표 달성.

## 트레이드오프

- 파일 목록의 행/셀이 스크린리더(내레이터 등) 접근성 트리에 노출되지 않음. 스크린리더 지원이 필요해지면 이 방식 대신 "탭 전환 시 그리드 전체 리바인딩을 줄이는 구조 개선"으로 대체해야 함.
- 타일 뷰(ListBox)와 컴팩트 뷰는 이번에 손대지 않음. 해당 뷰에서 같은 증상이 보이면 동일 기법 적용 가능.

## 롤백 방법

이번 변경분만 되돌리면 됨 (다른 미커밋 수정사항 주의 — `git checkout` 일괄 사용 금지):

1. `WorkFileExplorer.App/Controls/AutomationQuietDataGrid.cs` 삭제
2. `MainWindow.xaml`에서 `controls:AutomationQuietDataGrid` → `DataGrid`로 되돌리기 (여는 태그 3곳 + 닫는 태그 3곳)
3. (선택) 계측 제거: `Helpers/DispatcherDiag.cs` 삭제, `App.xaml.cs`의 `DispatcherDiag.Init(Dispatcher);` 한 줄 삭제, `LiveTrace.cs`의 `uiaFlags` 블록 제거 — 단, Debug 빌드에서만 동작하므로 남겨둬도 무방

## 참고

- 진단 로그: 실행 폴더의 `live_trace.log` (Debug 빌드에서 자동 생성, Release는 `KEXPLORER_LIVETRACE=1` 환경변수로 활성화)
- 관련 배경: WPF는 UIA 클라이언트가 이벤트를 구독하기 전까지는 접근성 이벤트를 만들지 않음. 메뉴/팝업 표시가 시스템 UIA 클라이언트의 구독을 유발하는 것은 WPF DataGrid류 앱에서 알려진 성능 이슈 패턴.
